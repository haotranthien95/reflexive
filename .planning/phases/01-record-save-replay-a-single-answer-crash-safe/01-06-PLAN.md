<objective>
Close verification Gap 4: `HistoryScreen` and `SessionDetailScreen` coerce a failed database read into an empty list and render the "No recordings yet" empty state. For a phase whose entire premise is "nothing you captured is ever lost", displaying a transient read error as total data loss is the worst possible failure presentation. Then fix the double-open defect that produces exactly that class of read error, and reconcile the requirement tracking that `01-VERIFICATION.md` flags as inconsistent.

**User story (MVP mode):** **As a** learner who has been recording answers for weeks, **I want to** be told the truth when the app cannot read my history — not shown an empty list — **so that** a temporary glitch never makes me believe my practice is gone.

Purpose: the persistence layer built in Plans 1 and 3 is genuinely solid and its reads are pure. The remaining defect is entirely in how a failure is *reported*, plus one reachable cause of that failure. Both are cheap to close and both sit directly on the phase's core promise.

Output: a distinct, retryable error state on both history screens; a database that cannot be opened twice; honest feedback when a recording file has gone missing; and a `REQUIREMENTS.md` that matches reality.
</objective>
