  <options>
    <option id="option-a">
      <name>Firestore native Timestamp; document ID is the Firestore auto-ID and IS the schema's `id`</name>
      <pros>`orderBy('created_at')` sorts chronologically and correctly forever with no format
      discipline required of any future writer. Phase 4's importer can use the server clock rather
      than the phone's. Auto-IDs never collide across repeated imports. No duplicated `id` field
      inside the document that can drift out of sync with the document's real key.</pros>
      <cons>The imported JSON format carries no `created_at`, so the importer must synthesise one
      (this is already required by IMPORT-03). A console or JSON export shows a timestamp object
      rather than a human-readable string.</cons>
    </option>
    <option id="option-b">
      <name>ISO-8601 UTC string (fixed width, e.g. 2026-08-09T06:44:10.685Z); auto-ID document key</name>
      <pros>Lexicographic string ordering equals chronological ordering for fixed-width UTC, so
      `orderBy` still works. Human-readable in the Firestore console and in any raw export. Trivially
      portable if the bank ever moves off Firestore.</pros>
      <cons>Correctness depends on every future writer emitting the exact same fixed-width UTC form —
      a local-time or offset-bearing string sorts wrong silently. The writing client's clock, not the
      server's, decides bank order.</cons>
    </option>
    <option id="option-c">
      <name>Integer epoch milliseconds; auto-ID document key</name>
      <pros>Unambiguous and numerically sortable with no format discipline at all. Smallest payload.</pros>
      <cons>Unreadable in the console, which matters because the console is the only bank-inspection
      tool this project has until Phase 4. Still client-clock-sourced.</cons>
    </option>

  `questionsFor(config)` issues the real filtered query: `where('subject', whereIn: config.topics)`
  AND `where('level', isEqualTo: config.level)` AND `orderBy('created_at')` ascending — a genuine
  server-side query, never an in-memory filter over the subjects read (D-32), and exact level matching
  with no widening and no CEFR ordering encoded anywhere (D-40). It maps each document's `content` to
  a prompt string.

  **The cache-versus-server rule, which is this phase's sharpest correctness detail.** Firestore's
  default read source is server-then-cache, so an offline read resolves successfully from an empty
  cache with zero documents. Taken at face value that renders "the bank is empty" to a user whose bank
  is full and whose signal is down. Therefore, in BOTH methods: a zero-document snapshot whose
  `metadata.isFromCache` is true must throw `QuestionBankUnavailableException` rather than return an
  empty list; a zero-document snapshot with `isFromCache` false returns an empty list, meaning the
  server genuinely confirmed emptiness; any thrown `FirebaseException` is logged via `debugPrint`
  (never surfaced) and rethrown as `QuestionBankUnavailableException`. No Firestore type — no
  `QuerySnapshot`, no `DocumentSnapshot`, no `FirebaseException` — crosses the seam; only
  `List<String>` out and this local exception type, exactly the containment rule
  `recording_service.dart` documents for its own seam.
