<objective>
Turn the tracer's single happy path into the four honest read outcomes the phase promises (D-37): the
topics card tells the user whether it is loading, genuinely empty, or unreachable; the Start button shows
work in flight; and a Start query that comes back with nothing says which of the level and the topics
to change. This is the plan that makes "a read failure is never presented as missing data" — Phase 1
Plan 6's rule — true for the question bank.

Purpose: after plan 01 a networked, happy-path user can drill real questions. After this plan an
offline user, a user with an empty bank, and a user who picked a level nobody has written questions
for each get told the truth instead of a spinner or a lie.

Output: `lib/screens/setup_screen.dart` carrying all four topics-card states and all three
Start-button states, a scripted `FakeQuestionSource` covering every outcome on the host, and an
adapter that skips malformed documents and, should a topic selection ever exceed Firestore's
confirmed `whereIn` limit, fails loudly rather than silently trimming the selection to fit.
</objective>

checkbox row is unpickable and meaningless. Each skip emits one `debugPrint` naming the document ID
and the reason, so a malformed import is diagnosable from the console; nothing about a skip reaches
the screen. Do not throw on a malformed document: one bad row must not take out the whole bank.

Extract the shared judgement as one pure, top-level helper `String? sanitizedText(Object? raw)` —
returning the trimmed value when `raw` is a `String` with non-whitespace content and `null` otherwise
— and use it from both reads, so the two can never drift into disagreeing about what "usable" means.
Being pure it is host-testable without a Firestore handle, which is what makes this task's tests
possible at all under D-47.

**The `whereIn` limit is a hard, loud edge — never a silent truncation.** Firestore caps the number of
values in a `whereIn` clause. Confirm the exact limit for the installed `cloud_firestore` version
rather than assuming one — check the package's own documentation via Context7 or the FlutterFire docs,
and record the number and its source in the SUMMARY. Declare it as a top-level
`const int kMaxTopicsPerQuery` whose doc comment carries the confirmed number and where it was
confirmed. Before issuing the query, `questionsFor` compares `config.topics.length` against that
constant; if the selection is wider it emits one `debugPrint` naming the real cause and throws
`QuestionBankUnavailableException`. It does NOT trim the topic list and it does NOT return a partial
bank. Silently dropping topics would be exactly the harm this plan's own BANK-03 prohibition forbids
for `question_count` and the CEFR level — altering what the user asked for without saying so — applied
to topics instead.

A multi-batch merge was considered and deliberately rejected. The seeded bank has five subjects
against a limit an order of magnitude larger, so the merge path is unreachable code this phase, and
the project's stated hard constraint is the leanest code with no speculative abstractions. State that
in the doc comment along with the named trigger that would reverse the call: if the bank ever grows
past `kMaxTopicsPerQuery` distinct subjects — Phase 4's in-app JSON importer (IMPORT-01) is the thing
that could do it — batching stops being speculative and becomes required, and that is the phase that
should build it. The user-facing surface for the throw is the existing Start-failure helper, whose
copy names the connection; that wording is imprecise for this one cause and is accepted deliberately
because the branch is unreachable at the current bank size (see the flagged assumption at the foot of
this plan). Do not add a fourth helper key, a fourth failure string, or any new UI for it.

Keep the containment rule intact: no `QuerySnapshot`, no `DocumentSnapshot`, no `FirebaseException`
leaves this file; the seam still returns `List<String>` and throws only
`QuestionBankUnavailableException`.
