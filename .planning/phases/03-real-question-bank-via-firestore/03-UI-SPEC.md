# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This phase EXTENDS the Phase 1 + Phase 2 design system — it does not replace it.** Every token below
is already implemented in `lib/main.dart` (`EnglishReflexApp` colour constants + `ThemeData.textTheme`).

Phase 3 introduces **zero new design tokens and zero new spacing exceptions**: no palette entry, no
font family, no font-size step, no new fixed geometry. Every new surface is assembled from values the
app already ships. The phase's entire UI surface is **three new states on one existing card** and
**three new states on one existing button**, both on the Setup screen.

**The practice screen, the history screen and the session-detail screen are visually untouched.** The
loop is handed a resolved `List<String>` at construction (D-34) and never learns where it came from,
so there is **no new `PracticePhase`, no new `kPhaseControlKeys` entry**, and no new failure path
inside the session.

Upstream sources: `03-CONTEXT.md` (D-32..D-47, locked), `02-UI-SPEC.md` (approved), `01-UI-SPEC.md`
(locked design system), `REQUIREMENTS.md` (SETUP-01, BANK-01..03, UI-01, UI-02). No `RESEARCH.md`
exists for this phase; stack facts are taken from `.claude/CLAUDE.md` and the Phase 1–2 implementation
in `lib/`.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Flutter project; shadcn and component registries are a web (React/Next/Vite) concept and are **not applicable** here |
| Preset | not applicable |
| Component library | Flutter Material 3 (`ThemeData(useMaterial3: true)`), no third-party UI kit. Phase 3 adds only stock `CircularProgressIndicator`, `Icon`, `TextButton` and `Row` — every one of them already used elsewhere in this app |
| Icon library | Material Icons (stock default per CLAUDE.md — do not add a second icon package). Phase 3 uses exactly one icon that is not already on screen: `Icons.error_outline_rounded`, reused verbatim from `_HistoryError` |
| Font | **Display/Heading:** `Baloo 2` (bundled `assets/fonts/Baloo2-SemiBold.ttf`). **Label/Body:** Flutter default Material font. Unchanged |

**Design tokens are Dart, not CSS.** Every value below is a Flutter logical pixel (dp) expressed as an
`EdgeInsets`/`SizedBox`/`fontSize`, and every colour is read through `Theme.of(context).colorScheme` —
screens never hardcode a hex. Enforced by convention since Phase 1; unchanged.

**Font invariant that survives the network (D-39).** `GoogleFonts.config.allowRuntimeFetching = false`
**stays set** in `configureFonts()`. This phase gives the release build the `INTERNET` permission for
the first time, which means a runtime font fetch would now *succeed* rather than fail loudly — exactly
the silent-degradation trap Phase 1 Plan 5 closed. The guard is what `test/theme/typography_test.dart`
asserts on, and it is about the font never fetching, not about the permission. `Firebase.initializeApp()`
joins `configureFonts()` in `main()` before `runApp`; it must **not** displace or reorder it.

**Package note (traceable to D-44):** `firebase_core` and `cloud_firestore` are added this phase. Both
have **zero UI surface** — they contribute no widget, no icon, no theme, and no user-visible affordance.
Every visual consequence of this phase is authored in `lib/screens/setup_screen.dart`.

## Spacing Scale

Unchanged from Phases 1–2. All values are multiples of 4, used as Flutter logical pixels (dp):

| Token | Value | Usage in Phase 3 |
|-------|-------|------------------|
| xs | 4px | (unused by new surfaces) |
| sm | 8px | Footer helper-line → button gap; error-icon → text gap in the footer row |
| md | 16px | Topics-card error: icon → message gap and message → Retry gap; footer vertical padding |
| lg | 24px | Topics-card interior padding (existing); the in-button busy spinner diameter; the footer error icon |
| xl | 32px | (unchanged section rhythm) |
| 2xl | 48px | Topics-card error icon size; Retry `TextButton` minimum height |
| 3xl | 64px | Existing touch-target floors (topic rows, `START SESSION`, Retry minimum width) |

**Exceptions: NONE ADDED.** Every exception in force is carried verbatim from `02-UI-SPEC.md`
(96px STOP circle, 64px primary-button height, min 64×48 secondary text button, 64px list-row floor,
120/144px mascot, 96px countdown ring, 160px numeral box, 48px app-bar icon buttons).

**Deliberate non-exception — the topics card is not height-locked.** The card's four states
(loading ≈ 90px, empty ≈ 100px, could-not-load ≈ 150px, populated ≈ 64px × N) have genuinely different
natural heights, and reserving the tallest would leave dead peach space in the common populated case.
The card therefore **sizes to its state**, and the content below it shifts when the state changes. This
is safe because the Setup body is already a `SingleChildScrollView` and the `START SESSION` footer is
pinned outside it, so nothing the user needs can be pushed off-screen. A fixed-height slot was
considered and rejected as an invented token buying stability the screen does not need.

**44px touch-target floor holds.** The new "Try again" `TextButton` takes the established
`minimumSize: Size(64, 48)`. The `START SESSION` button keeps its 64px height in all three of its
states, including busy — the busy state must not resize the button.

## Color

Unchanged from Phases 1–2. All four values remain `static const Color` fields on `EnglishReflexApp`:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFF8F0` warm ivory | Setup background; the Start footer background |
| Secondary (30%) | `#FFDDB3` soft peach | The topics card in **all four** of its states — the card stays peach whether it is loading, empty, failed or populated |
| Accent (10%) | `#FF6B35` coral-orange | See reserved-for list below |
| Destructive/Error | `#E5484D` warm red | **Icons only this phase** — see the new rule below |

Text on ivory/peach: `#3D2B1F` warm dark brown.

**Accent (`#FF6B35`) reserved for — the Phase 2 list, plus one addition:**

Items 1–13 are carried forward verbatim from `02-UI-SPEC.md`. Phase 3 adds exactly one:

14. The **topics-card loading spinner** — a `CircularProgressIndicator` at the Material default size,
    tinted `colorScheme.primary`. It qualifies under the standing rule that accent marks something
    *tappable or actively happening*: a spinner is the purest case of "actively happening", and at
    ≤48px it stays inside the "every other coral element must be ≤ a 48px control" budget.

**Not accent:** the `START SESSION` busy spinner. It sits *inside* a coral-filled button, so it is
brown `colorScheme.onPrimary` — the same brown-on-coral pairing (4.7:1) the STOP label, the switch
thumb and every other coral control already use. Coral-on-coral would be invisible.

**The two spinners can never appear at once.** The Start button is disabled while topics are loading,
and a background refresh (see Interaction Contract) shows no spinner at all. There is never more than
one coral "in-flight" signal on the screen.

### New rule — red marks the fault, brown carries the words

**`#E5484D` is used on icons only in this phase; every error *message* is warm brown `#3D2B1F`.**

This is a **narrowing** of Phase 2's "error red is never a fill" rule, not a contradiction, and it is
driven by measured contrast:

| Pair | Ratio | Verdict |
|------|-------|---------|
| `#E5484D` on peach `#FFDDB3` | **3.03:1** | Passes WCAG 1.4.11 non-text (3:1) → **icons OK**. Fails 1.4.3 text (4.5:1) → **not for 16px body** |
| `#E5484D` on ivory `#FFF8F0` | **3.72:1** | Same verdict — icon-safe, text-unsafe |
| `#3D2B1F` on peach `#FFDDB3` | **10.4:1** | Passes AA and AAA |
| `#3D2B1F` on ivory `#FFF8F0` | **12.8:1** | Passes AA and AAA |

So: the 48px `Icons.error_outline_rounded` in the topics card and the 24px one in the footer stay
error red and carry the "something went wrong" signal; the message text beside them is brown and is
comfortably legible. The "Try again" label is brown for the same reason — coral would be worse
(2.18:1 on peach), and a coral *filled* Retry would break the "at most one large coral surface per
screen" rule against `START SESSION`.

> **Pre-existing finding, out of scope, non-blocking.** `_HistoryError` (`lib/screens/history_screen.dart:170`)
> and the session-detail error state already render `kHistoryErrorMessage` in error red on ivory at
> **3.72:1**, below AA for 16px text. Phase 3 does not touch those screens and must not silently
> "fix" them mid-phase, but the finding is recorded here so it can be scheduled deliberately. The new
> Phase 3 surfaces deliberately do **not** copy that shortfall forward.

### Red vs. brown as a semantic, not just a contrast rule

The colour split doubles as the phase's honesty signal in the footer:

| Footer message | Icon | Text | Meaning |
|----------------|------|------|---------|
| "Pick at least one topic to start." | none | brown | **Change a setting** — a precondition you can satisfy |
| Zero-result (D-41) | none | brown | **Change a setting** — the bank has nothing for this level × topics |
| Query failure (D-38) | `error_outline_rounded`, red | brown | **Something went wrong** — retry, nothing is your fault |

A user must be able to tell "there is nothing to fetch" from "I could not fetch" at a glance — that is
the whole point of D-37/D-41 — and the icon is what carries it in a footer too small for a banner.

**Colour discipline rules carried forward unchanged:** at most one large coral surface per screen
(Setup: `START SESSION`); peach never sits on peach; peach marks content, never form chrome (the
topics card is the question-bank data surface, which is exactly why it becomes Firestore-backed here);
disabled controls use no accent and no error red.

### The two failure strings, and why there are two

Phase 1's convention is *one fixed user-facing string per failure*, with exception detail going only to
`debugPrint`/`FlutterError.reportError` and never to the screen. Phase 3 has **two distinct failures
with two distinct retry affordances**, so it gets two constants that share a first clause:

| Constant | Shown where | Retry affordance named in the copy |
|----------|-------------|-------------------------------------|
| `kTopicsErrorMessage` | Topics card, could-not-load state | "try again" — there is a **"Try again" button** right below it |
| `kQuestionLoadErrorMessage` | Start footer, after a failed Start query | "tap START SESSION again" — there is **no button**; re-tapping Start is the retry (D-38) |

Both follow `kRecordingErrorMessage`'s shape — *{what failed} — {what to do}* — and both say
**"couldn't reach"**, not "couldn't load" or "no questions". That verb choice is load-bearing: it names
the network as the suspect and therefore can never be misread as "your bank is empty", which is the
exact confusion D-37 exists to prevent.

### Zero-result copy (D-41) — names both dimensions, bounded in length

The message must name **the level and the topics**, because either could be the thing to change. It is
rendered in the footer, which does not scroll, so the topic list is enumerated only while it stays
short and collapses to a count beyond that:

| Selected topics | Copy |
|-----------------|------|
| 1 | **"No {level} questions in {topic} yet. Try another level, or pick more topics."** |
| 2 | **"No {level} questions in {topicA} or {topicB} yet. Try another level, or pick more topics."** |
| 3 or more | **"No {level} questions in any of your {n} topics yet. Try another level, or pick different topics."** |

Worked examples:
- *"No C2 questions in Travel yet. Try another level, or pick more topics."*
- *"No C2 questions in Travel or Food & health yet. Try another level, or pick more topics."*
- *"No C2 questions in any of your 4 topics yet. Try another level, or pick different topics."*

Design notes:
- **"yet"** is deliberate and warm — the bank is growable (Phase 4 import), so this is a temporary
  state, not a verdict.
- Both actions are offered in every variant, so the message is actionable regardless of which
  dimension is actually at fault.
- The 3+ variant still names the topic dimension (**"any of your 4 topics"**), satisfying D-41's
  both-dimensions requirement without an unbounded string in a non-scrolling footer.
- The 2-topic variant uses **"or"**, not "and" — the query is a disjunction (`subject in [...]`), and
  "and" would imply questions must match both.
- This is a formatted string, not a `const`. Author it as a single pure function (e.g.
  `String noQuestionsMessage(String level, List<String> topics)`) so all three branches are unit-testable
  on the host without a widget.

**A4 is constructed identically to `_HistoryError`** (48px icon → 16px → centred message → 16px →

`setup-topics-empty`, `setup-topics-error` or the checkbox rows is present at any time — the same
"deliberately total map" discipline `kPhaseControlKeys` already enforces on the practice screen. A
reachable topics state with none of these keys is a card that says nothing, and is not acceptable.

**Button state table:**

| State | Fill | Content | `onPressed` | When |
|-------|------|---------|-------------|------|
| C1 ready | coral `primary` | "START SESSION", brown Label 18/600 | the handler | topics loaded, ≥1 checked, no query in flight |
| C2 blocked | peach `surface` | "START SESSION", brown Label at **full opacity** | `null` | topics loading, bank empty, could-not-load, or none checked |
| C3 busy | **coral** `primary` | 24px `CircularProgressIndicator`, brown `onPrimary`, centred | `null` | the Start query is in flight (D-33) |

**C3 must keep the coral fill.** A busy button is an action *in flight*, not an action *blocked* — if
it fell back to the peach disabled treatment it would be visually identical to "you haven't picked a
topic", which is the opposite message. Because `FilledButton` paints `disabledBackgroundColor` whenever
`onPressed` is null, the busy state must explicitly override
`disabledBackgroundColor: colorScheme.primary` and `disabledForegroundColor: colorScheme.onPrimary`
for that frame. `onPressed: null` (rather than a swallowed tap) is deliberate and matches the D-19
precedent: a double-tap must be structurally impossible, not merely ignored.

**C3 carries no text**, so it must carry a semantic label instead:
`Semantics(label: 'Starting session', child: …)`. Give the spinner its own key `setup-start-busy` so a
widget test can assert the busy frame without depending on the semantics tree.

**The button never changes size between states.** 64px tall, full width, in all three. The 24px spinner
sits inside that fixed height with room to spare, so there is no layout shift on tap and none on
completion.

**Helper-slot totality.** At most one helper line renders, and B2/B3/B4 are mutually exclusive by
construction:

| Condition | Helper |
|-----------|--------|
| topics loading, or bank empty, or could-not-load | **B1 — nothing.** The card directly above already states what is happening *and*, in the failure case, owns the only Retry affordance. A second simultaneous message would make Setup the one screen in the app with two competing error surfaces |
| topics loaded, ≥1 subject, none checked | B2 |
| last Start query returned zero questions | B3 |
| last Start query threw | B4 |
| ready, or query in flight | B1 — nothing |

B3 and B4 can never coexist: a query either throws or returns, and each new tap replaces the previous
outcome. B2 cannot coexist with either: reaching a query at all requires ≥1 topic checked.

**Deliberate departure from the Phase 2 "disabled button and its reason always arrive together" rule.**
In the loading / empty / could-not-load cases the reason lives in the topics card rather than the
footer. The rule's *intent* — a disabled control is never unexplained — is satisfied, on the same
screen, by the more specific message, and in the failure case by the one that also carries the fix.
Duplicating it in the footer would be noise. This is recorded here so the checker reads it as a
considered narrowing rather than a regression.

## Interaction Contract

### The topics read lifecycle (D-35, D-37)

| Trigger | Current state | Behaviour |
|---------|---------------|-----------|
| `initState` | no data | → **A1 loading** → A2 / A3 / A4 |
| "Try again" tap | A4 could-not-load | → **A1 loading** → A2 / A3 / A4 |
| Setup reappears (pop from Practice or History) | A2 or A3 (data on screen) | **Background refresh** — see below |
| Setup reappears | A4 could-not-load | → **A1 loading** (there is nothing worth keeping) |

**Background refresh is stale-while-revalidate, and it is silent.** When Setup reappears with topics
already on screen, the re-read (D-35) runs **without** flipping the card to A1 and **without** showing
a spinner:

- **On success:** the subject list is replaced. If the new list differs, the card simply re-renders.
- **On success with zero server-confirmed documents:** the card flips to A3 empty and all selections clear.
- **On failure:** the last-known topics **stay on screen**, the card does not flip to A4, and the
  exception goes to `debugPrint` only.

Rationale: A1 and A4 are *"there is nothing on screen"* states. Replacing good, usable data with a
spinner or an error because a refresh failed would be a regression in usability and would flicker the
checkboxes on every return from History. Nothing is hidden that the user can act on — if the bank is
genuinely unreachable, the Start query has its own honest failure surface (B4) one tap away.

**Selection reconciliation is mandatory after every successful read:**

```
selectedTopics = selectedTopics ∩ newSubjects
```

Without this, a topic that disappeared from the bank could survive in `_selectedTopics`, travel into
`SessionConfig.topics`, and become a `where subject in [...]` clause filtering on a value that does not
exist — a silent zero-result the user cannot explain. Dropping it is the honest outcome: a topic that
is not on screen must not be in the session.

**The orphan-sweep ordering contract is undisturbed.** `_sweepOrphanRecordings()` and the subjects read
both start in `initState` and neither awaits the other. `pruneOrphanRecordings` must still complete
before any recording filename is chosen — and this phase makes that *easier*, not harder, because Start
now takes a network round trip before `PracticeScreen` is even pushed.

### The empty-vs-unreachable rule — the phase's sharpest correctness detail

**An empty result may only render A3 ("No topics yet") when the server confirmed it.**

`cloud_firestore`'s default read source is server-then-cache: when the device is offline, a query
resolves from the on-device cache instead of failing, and **an empty cache produces a successful,
zero-document snapshot**. Taken at face value that renders "No topics yet" — telling a user with a full
bank and no signal that their questions are gone. That is precisely the failure Phase 1 Plan 6 was
written to prevent and that D-37 re-states for the bank.

The contract is therefore:

| Read outcome | State |
|--------------|-------|
| ≥1 document | **A2 populated** (regardless of cache or server) |
| 0 documents **and** `snapshot.metadata.isFromCache == false` | **A3 empty** — the server genuinely says the bank is empty |
| 0 documents **and** `snapshot.metadata.isFromCache == true` | **A4 could-not-load** — this is an unserved read, not an empty bank |
| threw | **A4 could-not-load** |

`QuerySnapshot.metadata.isFromCache` exists in current `cloud_firestore` for exactly this reason: an
empty snapshot contains no documents to inspect, so the metadata flag is the only way to distinguish
"nothing there" from "nobody answered". Both offline shapes — throw *and* empty-from-cache — land on
the same honest state, so the contract holds whichever way the SDK behaves on a given platform.

**The same rule applies to the Start query.** A zero-document result that came from the cache is a
failure (B4), not a zero-result (B3). B3 is reserved for a server-confirmed "this level × these topics
has nothing", because only then is "try another level" true advice.

*Implementation note for the planner:* the `QuestionSource` seam returns plain `List<String>`, so the
cache/server distinction must be resolved **inside** `FirestoreQuestionSource` and surfaced as a thrown
exception rather than an empty list. That keeps the fake source in tests trivially able to produce all
four states (return topics / return empty / return `[]` / throw) with no Firestore types leaking into
the seam — which is exactly what D-47 asks for.

### The Start flow (D-33, D-38, D-41)

1. Tap `START SESSION` (only reachable in C1).
2. The button enters **C3 busy**; any existing B3/B4 helper clears.
3. A `SessionConfig` is built from the current control values — **this is a snapshot** (see the race
   note below) — and the filtered query runs.
4. Outcome:
   - **≥1 question** → `PracticeScreen` is pushed with the resolved `List<String>`. The button returns
     to C1 behind the push, so popping back finds a normal footer.
   - **0 questions, server-confirmed** → button returns to C1, helper shows **B3**.
   - **threw, or 0 questions from cache** → button returns to C1, helper shows **B4**.
5. **Every setting survives every outcome** (D-38): topics, level and all three sliders are untouched.
   Nothing is reset, and no navigation happens on a failure — the user never loses their setup to a
   network problem.

**Helper messages clear on the next meaningful action.** B3 and B4 both describe a specific
(topics × level) attempt, so both clear when the user changes **any** topic, the level, or any slider,
and when Start is tapped again. A stale "No C2 questions in Travel yet." sitting under a now-B1
configuration would be a lie.

**`PracticeScreen` is pushed only with questions in hand.** Its Phase 2 constructor contract — handed
everything it needs, discovers no dependency mid-session — is preserved exactly. After the push there
is no code path from the practice screen to Firestore: not a lazy one, not a retry, not a cache
refresh. The loop stays provably network-free as a structural property, not a discipline.

### Offline behaviour has no dedicated UI (D-36)

There is no offline banner, no connectivity indicator, and no "you're offline" state. The Firestore
on-device cache serves both reads transparently after one successful online Setup visit, so a plane-mode
session simply works and looks identical to an online one. A genuinely first-run-offline device has an
empty cache and lands on **A4** with copy that names the connection — which is the correct and complete
treatment. Adding a connectivity affordance would mean a new dependency, a new state, and a new thing
to be wrong about, for a case the existing failure state already explains.

### Interaction races

| Item | Status | Resolution |
|------|--------|------------|
| A setting is changed while the Start query is in flight | ⚠ **unresolved** | The controls remain interactive during C3 (no invisible disabling, no full-screen overlay — both were rejected as heavier than the ~sub-second window warrants). **Planner assumption: the config snapshotted at tap time wins**, so a change made mid-flight applies to the *next* Start, not the one in progress. This mirrors the "first signal wins" principle already used for the Phase 1 auto-stop-vs-manual-Stop race and the Phase 2 auto-stop-vs-Pause race. It must become an explicit test case rather than an inherited convention. If on-device timing shows the query routinely exceeding ~1 s, revisit — the sanctioned upgrade is to disable the form controls during C3, never to add an overlay |
| "Try again" tapped twice while a topics read is in flight | ✅ covered | A4 is replaced by A1 on the first tap, and A1 has no Retry button — the second tap is structurally impossible, exactly as C3's `onPressed: null` makes a double-Start impossible |
