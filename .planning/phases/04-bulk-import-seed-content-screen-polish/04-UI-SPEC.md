# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This phase EXTENDS the Phase 1 + 2 + 3 design system — it does not replace it.** Every token below is
already implemented in `lib/main.dart` (`EnglishReflexApp` colour constants + `ThemeData.textTheme`).

**Phase 4 introduces zero new colours, zero new font families, zero new font sizes, zero new font
weights and zero new spacing exceptions.** Its entire UI surface is:

1. **One new `IconButton`** in `SetupScreen`'s existing AppBar `actions:` list (D-48).
2. **One new modal bottom sheet** — the importer — assembled entirely from widgets and tokens the app
   already ships (D-48, D-50, D-51, D-55, D-60, D-62).
3. **One new helper string** in the existing Setup Start footer, for the >30-topics case (D-61).
4. **One new call site** for the existing `_refreshSubjectsOnReappear()` (D-51).
5. **A written navigation contract** that makes UI-03 checkable rather than arguable (D-49).

**No route is pushed.** The practice screen, the history screen and the session-detail screen are
visually and behaviourally untouched. The practice loop still never reaches the network.

Upstream sources: `04-CONTEXT.md` (D-48..D-63, locked), `03-UI-SPEC.md` (approved), `02-UI-SPEC.md`
(approved), `01-UI-SPEC.md` (locked design system), `REQUIREMENTS.md` (IMPORT-01..05, UI-01..03),
`.claude/CLAUDE.md` (stack + Conventions). No `RESEARCH.md` exists for this phase; stack facts are taken
from CLAUDE.md and from the Phase 1–3 implementation in `lib/`.

## Navigation Contract (UI-03, D-49)

**UI-03 is discharged by this inventory, not by an argument.** `lib/screens/` contains four files and
UI-03 says three; the requirement cannot be checked off without a written rule for what it counts.

**Definition — a *core screen* is a top-level destination that:**
1. the user navigates **to** from the app's own chrome (an app-bar action or a primary CTA), **and**
2. owns a distinct task the user can stay in indefinitely, **and**
3. is reachable without first opening another destination's content.

A drill-down of a list item, a modal sheet and a modal dialog each fail at least one clause and are
therefore **not** core screens.

### Complete route + surface inventory (every navigable surface in the app)

| Surface | Reached from | Pushes a route? | Classification |
|---------|--------------|-----------------|----------------|
| `SetupScreen` | `MaterialApp.home` | — (root) | **Core screen 1 of 3** |
| `PracticeScreen` | Setup `START SESSION` | yes (`MaterialPageRoute`) | **Core screen 2 of 3** |
| `HistoryScreen` | Setup AppBar `Icons.history` | yes (`MaterialPageRoute`) | **Core screen 3 of 3** |
| `SessionDetailScreen` | tapping a row **inside** History | yes (`MaterialPageRoute`) | **Detail view** — fails clause 3 (unreachable without opening a History row) and clause 1 (reached from content, not chrome) |
| **Import bottom sheet (NEW)** | Setup AppBar `Icons.upload_file` | **no** — `showModalBottomSheet` pushes a modal, not a page | **Modal** — fails clause 2 (a transient maintenance task with a single terminal outcome) |
| Stop-confirmation `AlertDialog` | Practice AppBar Stop / back gesture | no | **Modal** — unchanged from Phase 2 |
| Snackbars / banners | in-place | no | **In-place feedback** — not destinations |

**Result: exactly 3 core screens (Setup, Practice, History), 1 detail view, 2 modals, 0 extraneous
navigation. UI-03 holds.**

**The rule that keeps it holding:** any future surface that would push a `MaterialPageRoute` from
app-bar chrome or from a primary CTA becomes a fourth core screen and must either justify itself against
UI-03 or be built as a modal/detail view. **This is exactly why D-48 chose a bottom sheet** — a
full-screen pushed route would have made the route count five in the one phase whose requirement is
"exactly 3 screens with no extraneous navigation". The screen count is unchanged **by construction**,
not by argument.

## Spacing Scale

Unchanged from Phases 1–3. All values are multiples of 4, used as Flutter logical pixels (dp):

| Token | Value | Usage in Phase 4 |
|-------|-------|------------------|
| xs | 4px | (unused by new surfaces) |
| sm | 8px | Progress-bar height; summary-count line spacing; skip-row reason → question-text gap; icon → text gap in the Start footer's new helper |
| md | 16px | Sheet bottom padding; failure-state icon → message and message → button gaps; gap **between** skip-list rows; caption → progress-bar gap |
| lg | 24px | Sheet horizontal + top padding; peach card interior padding; sheet top-corner radius; in-sheet spinner diameter; title → body and body → button gaps |
| xl | 32px | (unchanged section rhythm; unused by new surfaces) |
| 2xl | 48px | Sheet failure-state error icon size |
| 3xl | 64px | Sheet primary-button height (existing primary-button floor); AppBar action row (2 × 48px `IconButton`) |

**Exceptions: NONE ADDED.** Every exception in force is carried verbatim from `02-UI-SPEC.md` /
`03-UI-SPEC.md` (96px STOP circle, 64px primary-button height, min 64×48 secondary text button, 64px
tappable-list-row floor, 120/144px mascot, 96px countdown ring, 160px numeral box, 48px app-bar icon
buttons).

**Deliberate non-exception 1 — the sheet is not height-locked.** Its eight states have genuinely
different natural heights (idle ≈ 320px, checking ≈ 200px, writing ≈ 240px, a clean result ≈ 280px, a
result with 40 skipped rows ≈ unbounded). It is shown with `isScrollControlled: true` and a
`Column(mainAxisSize: MainAxisSize.min)` inside a `SingleChildScrollView`, capped at **90% of screen
height** via `constraints`, so it sizes to its state and scrolls when the skip list is long — exactly
the reasoning that left the Phase 3 topics card unlocked. A fixed-height sheet was considered and
rejected as an invented token buying stability nothing needs.

**Deliberate non-exception 2 — skip-list rows are exempt from the 64px row floor.** That floor exists
for **tappable** rows (history rows, topic checkboxes, the replay toggle). A skip row is read-only
static content with no gesture attached; pinning it to 64px would make a 40-row list three screens tall
for no accessibility gain. Skip rows size to their text and are separated by **16px (md)**.

**44px touch-target floor holds.** The new AppBar `IconButton` takes the Material 48px default. Every
in-sheet button is either the 64px full-width primary or a `TextButton` at the established
`minimumSize: Size(64, 48)`.

**The sheet has no text input**, so `viewInsets` keyboard handling is not a concern; `useSafeArea: true`
plus the sheet's own 16px bottom padding keeps the primary button clear of the home indicator.

## Typography

Unchanged from Phases 1–3 — exactly **4 sizes and 2 weights**, all already in `lib/main.dart`. Phase 4
adds **no fifth size, no third weight and no third font family**:

| Role | Theme slot | Size | Weight | Line Height | Family |
|------|-----------|------|--------|-------------|--------|
| Body | `bodyLarge` | 16px | Regular (400) | 1.5 | Default Material |
| Label | `labelLarge` | 18px | SemiBold (600) | 1.2 | Default Material |
| Heading | `headlineSmall` | 24px | SemiBold (600) | 1.2 | Baloo 2 |
| Display | `displayLarge` | 32px | SemiBold (600) | 1.3 | Baloo 2 |

**Phase 4 role assignments (every new element):**

| Element | Role |
|---------|------|
| Sheet title ("Import questions") | Heading |
| Result headline ("85 questions added") | Heading |
| Idle-state instruction line | Body |
| **JSON shape example block** | Body — see the monospace note below |
| Busy captions ("Checking your file…", "Comparing with your bank…", "Saving 600 questions to your bank…") | Body |
| "Keep this open until it finishes." | Body |
| Result sub-counts (duplicates, skipped) | Body |
| Skip-list section label ("What we skipped") | Label |
| Skip-row reason line ("Row 14 · level "B7" isn't one of A1–C2") | Body |
| Skip-row question text (truncated to one line) | Body |
| Every file/bank failure message | Body |
| Every in-sheet button label ("Choose a JSON file", "Choose a different file", "Try again", "Done") | Label |
| Setup Start footer >30-topics helper | Body |
| AppBar import action | icon-only + tooltip — **no text** |

**No monospace family is introduced, deliberately.** The JSON shape example (D-50) is the one element
that would conventionally take a code font. Adding one would be a **third font family** in a contract
that declares two, for a three-line hint. The example therefore renders at **Body 16/400 brown inside a
peach card**, pre-broken into short lines, with `softWrap: true`:

```
{"data": [
  {"content": "…", "subject": "…", "level": "A2"}
]}
```

It is a hint to recognise, not code to copy — legibility, not glyph alignment, is what it needs. It is
plain `Text` (see Untrusted Input), never `SelectableText` and never an editable field.

**`textScaler` is never pinned (UI-01).** `MaterialApp` still has no `builder:` MediaQuery override.
Every new surface must survive the largest OS text-scale setting by growing, wrapping or scrolling —
never clipping:

- The sheet body is a `SingleChildScrollView`; the primary button sits **inside** it at the bottom of
  the column (not pinned), so at extreme scale the user scrolls to it rather than losing it behind a
  taller body. The 90%-height cap guarantees the scrim and the drag handle stay visible, so the sheet
  never reads as a full screen.
- The JSON example wraps rather than clipping (backstop — see UI Considerations).
- Skip-row question text is the **one deliberate truncation** in the app: `maxLines: 1`,
  `overflow: TextOverflow.ellipsis`. The reason line above it is never truncated, because the reason is
  the actionable half.
- The Setup Start footer's new helper obeys the existing footer rule: `Column(mainAxisSize: min)` below
  an `Expanded` scroll view, so a taller helper shrinks the scroll area rather than overflowing.

## Color

Unchanged from Phases 1–3. All values remain `static const Color` fields on `EnglishReflexApp`:

| Role | Value | Usage in Phase 4 |
|------|-------|------------------|
| Dominant (60%) | `#FFF8F0` warm ivory | The bottom sheet's own surface; the sheet's skip-list background |
| Secondary (30%) | `#FFDDB3` soft peach | The JSON-example card; the result summary card; the progress-bar track |
| Accent (10%) | `#FF6B35` coral-orange | See the reserved-for list below |
| Destructive/Error | `#E5484D` warm red | **Icons only** — carried forward from Phase 3's narrowing |

Text on ivory/peach: `#3D2B1F` warm dark brown.

**The sheet surface is ivory, not peach.** A modal sheet is *chrome* — a container for content — and the
standing rule is **peach marks content, never form chrome**. The two peach cards inside it (the JSON
example, the result summary) are the content. This also keeps the "peach never sits on peach" rule
intact: the skip list sits directly on ivory beneath the peach summary card, with no card of its own.

**Accent (`#FF6B35`) reserved for — the Phase 3 list of 14, plus two:**

Items 1–13 are carried from `02-UI-SPEC.md`; item 14 (the topics-card loading spinner) from
`03-UI-SPEC.md`. Phase 4 adds exactly two:

15. **The import sheet's primary button fill** — "Choose a JSON file" / "Choose a different file" /
    "Try again" / "Done". Exactly one is present at a time, so the sheet carries **at most one coral
    surface**.
16. **The write-progress bar** — a determinate `LinearProgressIndicator`, coral `value` on a peach
    `backgroundColor`, **8px tall, radius 4**, full sheet width. It qualifies under the standing rule
    that accent marks something *tappable or actively happening*, and at an 8px stroke it stays inside
    the "every other coral element must be ≤ a 48px control or a ≤ 8px stroke" budget.

**The AppBar import icon needs no new entry.** `appBarTheme.actionsIconTheme` already paints every
AppBar action coral, and "the app bar's primary icon" has been on the reserved list since Phase 1. The
import icon simply joins the history icon under an existing rule.

**The in-sheet indeterminate spinner is covered by item 14** — same widget, same coral, same "actively
happening" justification as the topics-card spinner. No new entry.

### The one-large-coral-surface rule, and why the sheet does not break it

The standing rule is **at most one large coral surface per screen** (on Setup, that is `START SESSION`).
While the sheet is open, `START SESSION` sits **behind the modal barrier scrim** and is visually
recessed and untappable, while the sheet's own primary button is the single live coral surface. The rule
is satisfied at every frame; it is only ever *two* coral surfaces in the same pixel space, one of them
scrimmed. This is recorded here so the checker reads it as a considered narrowing rather than a
regression.

### Red marks the fault, brown carries the words (carried forward unchanged)

Phase 3's measured narrowing applies verbatim to every new failure surface:

| Pair | Ratio | Verdict |
|------|-------|---------|
| `#E5484D` on ivory `#FFF8F0` | 3.72:1 | icon-safe (WCAG 1.4.11, 3:1); **text-unsafe** (1.4.3, 4.5:1) |
| `#3D2B1F` on ivory `#FFF8F0` | 12.8:1 | AA + AAA |
| `#3D2B1F` on peach `#FFDDB3` | 10.4:1 | AA + AAA |

So in the sheet: the 48px `Icons.error_outline_rounded` is error red; **every message beside or beneath
it is brown**; every button label is brown (on coral fill, 4.7:1, the same pairing STOP already uses).

### Red vs. brown as the phase's honesty semantic

The colour split is what lets the user tell the five different facts apart at a glance — the write-path
extension of D-37:

| Surface | Icon | Text | Meaning |
|---------|------|------|---------|
| Result: "85 questions added" | none | brown | **It worked** |
| Result: "12 were already in your bank" | none | brown | **Neutral fact** — a duplicate is *not* an error and never gets red |
| Result: "3 rows were skipped" + skip list | none | brown | **Your file needs an edit** — a per-row problem, not a system failure |
| File problem (D-62) | red 48px | brown | **That file can't be used** — pick another |
| Bank unreachable (D-60) | red 48px | brown | **Something went wrong** — nothing was written, retry |
| Partial write | red 48px | brown | **Something went wrong mid-way** — here is exactly how much landed |
| Setup: >30 topics (D-61) | **none** | brown | **Change a setting** — a precondition you can satisfy |

**The >30-topics helper deliberately gets no icon**, unlike the sibling `kQuestionLoadErrorMessage`
failure that sits in the same footer slot. It is not a fault; it is a limit the user can satisfy by
unchecking a topic that is visible on the same screen. Giving it the red error icon would file it under
"something went wrong, retry" — the exact misreading D-61 exists to end.

**Colour discipline rules carried forward unchanged:** peach never sits on peach; peach marks content,
never chrome; disabled controls use no accent and no error red; error red is never a fill.

### Why "nothing was imported" and "anything already saved will be skipped" are load-bearing

IMPORT-04 forbids a silent or partial failure. Two of the strings above are the copy-side of that
requirement, and neither may be softened:

- `kImportUnreachableMessage` says **"nothing was imported"** because D-60 gates the whole import behind
  a server-only read: when it fails, not one document has been written. Without that clause the user
  cannot tell this state from a partial write and would have no idea whether re-importing is safe.
- `importPartialMessage` states **the exact count that landed** and then names the recovery in the same
  breath. The recovery is only true because D-54 dedupes against the existing bank — re-importing the
  same file is *harmless by construction*, and saying so turns the one genuinely partial outcome in this
  phase from a dead end into a one-tap fix.

### Why a duplicate never gets error treatment

"12 were already in your bank" is **neutral, past-tense and un-iconed**. A user re-importing a file
should feel reassured, not warned — the app is telling them their bank is already correct. Duplicates
are also **never listed per row**: enumerating 400 duplicate rows would bury the 3 rows that actually
need an edit, which is the opposite of what D-55's skip list is for.

### Skip-reason copy rules

- **Position first, always.** `Row 14 · …` uses the row's **1-based position in the file** (D-55). A
  reason without a location tells the user a *shape* of problem, not a *place*; the position is what
  makes it findable in their editor.
- The interpunct `·` separates position from reason. It is a single glyph in both fonts and reads as a
  quiet separator rather than a hyphen (which the app's failure strings already use for "— what to do").
- **The offending level value is quoted back** (`level "B7"`) because it is the user's own text and it
  is the fastest way to find the row. It is **truncated to 12 characters with an ellipsis and stripped
  of newlines** before rendering — a "level" field containing 5,000 characters must not be able to blow
  up a row (see Untrusted Input).
- **A1–C2** is written as a range, not a six-item list, because it is the same range already printed on
  the Setup level chips the user has seen.
- Reason strings never say "invalid", "error" or "failed". "no question text", "no topic",
  "isn't one of A1–C2", "not shaped like a question" describe the row, not the user.

### Singular / plural is a pure function, not an interpolation

`importAddedLine`, `importDuplicatesLine`, `importSkippedLine` and `importSavingMessage` each have a
singular branch, a plural branch and (for the added line) a **zero** branch — "No questions added" reads
correctly where "0 questions added" reads like a bug. Author them as pure host-testable functions beside
`noQuestionsMessage()`, which set the precedent in Phase 3.

**Zero-suppression:** the duplicates line and the skipped line render **only when their count is > 0**.
The added line **always** renders. A clean import therefore shows exactly one line — "85 questions
added" — and nothing else, which is the resting shape of a success.

**Copy voice rules (carried from Phases 1–3):** warm, second-person, lowercase sentence case except the
all-caps action words (`STOP`, `RESUME`, `START SESSION` — "Done" is a dismissal, not a drill action, and
stays sentence case). Never blames the user. Never leaks an exception message, a Firestore error code, a
collection name, a document ID or a project ID to the screen. Ellipses mark transient states only.

#### S3 — Writing  `key: import-writing`


**The bar is determinate, and its granularity is honest.** `value = committedRows / rowsToWrite`, and it
advances **only when a `writeBatch` has actually committed** — never optimistically per row. For a

0 to 1. That is deliberately the *truthful* granularity: this app does not report a write it has not seen
acknowledged (D-60, and the Phase 1 / D-37 precedent).

*Rejected: a plain indeterminate spinner — simpler, but a multi-batch 600-row commit runs for seconds and
an unmoving spinner reads as a hang. Rejected: a per-row optimistic bar — smoother, and a lie.*

for the recording readout. Screen-reader users get one announcement, not one per batch.

## Interaction Contract

### The import flow, end to end

| Step | State | Dismissible? |
|------|-------|--------------|
| 1. Tap `setup-import` | sheet opens on **S1 idle** | yes |
| 2. Tap "Choose a JSON file" | OS document picker (`FileType.custom`, `['json']`) | OS-owned |
| 3a. **Picker cancelled** | back to **S1 idle**, unchanged, **no message** | yes |
| 3b. File chosen | **S2** "Checking your file…" | yes |
| 4. Read + parse + validate every row in memory (D-52, D-53) | S2 | yes |
| → unreadable / bad shape | **S5 file problem** | yes |
| → `data` is an empty list | **S6 file empty** | yes |
| 5. **Server-only** read of the bank for dedupe (D-60) | **S2**, caption → "Comparing with your bank…" | yes |
| → read fails | **S7 unreachable** — *no document has been written* | yes |
| 6. Dedupe against the bank and against earlier rows in the same file (D-54) | S2 | yes |
| 7. Write the surviving rows in `writeBatch` chunks | **S3 writing** | **NO** |
| → every chunk commits | **S4 result** | yes |
| → a chunk fails after an earlier one committed | **S8 partial write** | yes |
| 8. Dismiss (Done, drag, barrier tap, or system back) | sheet closes → **subjects re-read** | — |

**Cancelling the picker is not a failure and gets no copy.** Returning to the idle state with the format
hint still on screen is the complete and correct treatment.

### Dismissal: one refresh call site, every exit route (D-51)

**The re-read is wired to the `await` of `showModalBottomSheet(...)`, never to the "Done" button's
`onPressed`.** That single line covers *every* way the sheet can close — Done, drag-down, barrier tap and
system back — so there is exactly **one** refresh call site and no exit path that silently skips it:

```dart
await showModalBottomSheet<void>(...);
if (!mounted) return;
await _refreshSubjectsOnReappear();
```

**This wiring is mandatory and is not covered by existing code.** D-35's refresh runs off the
`Navigator.push` awaits in `_openHistory()` and `_startSession()`; a bottom sheet pops no route, so
without this call an import's new topics would not appear until the user left Setup and came back.
`_refreshSubjectsOnReappear()`'s doc comment currently predicts that Phase 4 "will need no extra wiring"
— that prediction is true for a pushed route and **false for a modal sheet**, and the comment must be
corrected in this phase.

**The refresh behaviour is Phase 3's, unchanged.** Sheet dismissal is treated **identically** to popping
back from History: a silent stale-while-revalidate refresh when topics are already on screen (no spinner
flash, no checkbox flicker), and a full loading state only when the card was in its could-not-load state.
A bank that gained its very first topic goes A3 → A2 silently, which is exactly right — the sheet has
already said "85 questions added" and a second announcement on Setup would be noise. Selection
reconciliation (`selectedTopics ∩ newSubjects`) still runs after every successful read.

### Dismissal is blocked in exactly one state, and only that one

| State | Drag / barrier / back | Why |
|-------|----------------------|-----|
| S1, S2, S5, S6, S7 | **allowed** | Nothing has been written. Leaving costs the user nothing |
| **S3 writing** | **blocked** | A user who closes mid-write never learns which rows landed — precisely the unreported partial outcome IMPORT-04 exists to prevent |
| S4 result, S8 partial | **allowed** | The outcome has been read; the refresh fires on every route |

Implement with `PopScope(canPop: !isWriting)` inside the sheet builder — the same mechanism the practice
screen already uses to route the back gesture into the Stop dialog (D-29). The write is short and its
caption already says **"Keep this open until it finishes."**, so a blocked gesture is explained *before*
it is attempted rather than after.

**Backstop:** whether drag-to-dismiss and barrier taps route through `PopScope` (as opposed to only the
system back gesture) is Flutter-version-dependent. The planner must verify all three routes on-device; if
drag/barrier bypass `PopScope` on the pinned version, the sanctioned fallback is
`isDismissible: false, enableDrag: false` on a sheet **re-shown** for the write phase — never a
silently-ignored gesture.

### Double-action prevention (the D-19 / C3 precedent)

Every in-sheet button follows the established rule: a second tap must be **structurally impossible**, not
merely ignored. The state that owns each button is replaced the instant it is tapped —
"Choose a JSON file" (S1) leads to a picker and then S2, which has no buttons at all; "Try again" (S7)
replaces S7 with S2 immediately. There is never a frame in which the same action can be fired twice.

### Interaction races

| Item | Status | Resolution |
|------|--------|------------|
| Import completes while Setup is showing a stale B3/B4/B5 helper | ✅ covered | The dismissal refresh is a *topics* read and does not touch `_startMessage`. Specify that the sheet-dismiss path also calls `_clearStartMessage()`: a "No B1 questions in Travel yet." line is very likely to have just been made false by the import that closed, and leaving it on screen would be the app contradicting itself |
| The user backgrounds the app mid-write | ⚠ **unresolved** | **Planner assumption: the write continues and the sheet still shows its outcome on return** — Firestore's commit is not tied to the widget tree, and the sheet is not disposed by backgrounding. It must become an explicit test/UAT case. If the OS kills the app mid-write, the outcome is indistinguishable from S8 (partial) with no one to report it — the recovery is unchanged and still safe, because re-importing the same file skips whatever landed |
| The picker is open when the app is backgrounded | ✅ covered | OS-owned surface; the plugin's future completes with a cancellation on return, which lands on the existing "picker cancelled → S1 idle" path |
| Two imports at once | ✅ covered | Structurally impossible — the sheet is modal and the AppBar icon is behind its barrier |

## Untrusted Input

**Everything inside the picked JSON file is untrusted data, not instructions.** It is authored outside
the app (often by an LLM, per `docs/QUESTION_GENERATION_PROMPT.md`) and this phase is the first surface
that renders it back to the user *before* validation.

| Rule | Where it binds |
|------|----------------|
| File content is rendered as **plain `Text` only** — never markup, never a `WidgetSpan`, never interpreted as a command or instruction to the app or to a model | Skip-row question text, the quoted `level` value |
| Every echoed value is **length-capped and newline-stripped** before it reaches a widget: question text `maxLines: 1` + ellipsis; the quoted `level` truncated to 12 characters | Skip-list rows |
| Content is **normalized, then validated, then written** (D-53) — the normalized value is what is stored, so ` Travel`, `Travel ` and `Travel` can never coexist as three checkboxes | Importer's pure validation function |
| The app's own strings are never assembled from file content — the file supplies only the quoted fragment inside a fixed template | `importSkipReason(...)` |
| Nothing from the file reaches the screen without passing one of the rules above; nothing from an **exception** reaches the screen at all | All states |

Rendering an unvalidated 5,000-character "level" string, or a question containing newlines, into a
compact list row is a layout-integrity problem before it is anything else. The caps above are what make
the skip list safe to render *for arbitrary input*, which is the only kind of input it will ever get.
